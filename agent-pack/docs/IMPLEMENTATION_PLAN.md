# 实施计划与完成定义

## Phase 0 — 只读仓库审计

输出：
- Git commit、工作区状态、Rust 版本。
- workspace/crate 与 app 结构。
- Web 前端启动与构建方式。
- `.rgis` 解析/序列化、保存/打开和图层引用的真实代码位置。
- 当前目录浏览、文件 provider、栅格路径、PostGIS provider 的实现位置。
- 现有测试命令及通过情况。
- 最小改动方案和文件列表。
- 明确哪些能力直接复用，哪些需要开发。

完成条件：没有代码修改；所有结论引用真实路径、符号和命令输出。

## Phase 1 — 基线与工程模型实验

任务：
- 固定上游 commit，建立可重复的构建与测试基线。
- 制作最小测试工程，验证保存/重新打开是否保留图层、样式、视图和数据源引用。
- 验证无效路径在当前加载流程中的行为。
- 确认工程是否内嵌某些矢量数据、是否引用栅格路径，记录格式的真实语义。

完成条件：有测试或可复现脚本；不改变产品行为。

## Phase 2 — 工程版本保护（优先）

任务：
- 建立工作副本与不可变版本的最小状态模型。
- 打开已保存版本时只读。
- 复制工程创建新的工作副本。
- 保存工作副本生成唯一新版本。
- 服务端拒绝覆盖已有版本；写入采用原子发布策略。
- 处理应用重启后的版本列表和恢复。

完成条件：
- 尝试覆盖已有版本返回明确冲突错误。
- 复制后修改不改变父版本。
- 重启后所有已发布版本仍可读取。
- 异常中断不会让半写入版本显示为有效版本。

## Phase 3 — 文件数据源配置与浏览

任务：
- 持久化多个目录根路径。
- 添加、删除、启用/禁用、重新扫描。
- 目录内支持文件浏览与分页。
- 新扫描发现的文件可浏览，但不会自动添加到工程。
- 路径访问限制在配置根目录内。

完成条件：
- 重启后目录列表保留。
- 新增目录、已有目录新增文件、删除文件三类变化都能正确反映。
- 路径穿越和符号链接逃逸测试通过。
- 大目录扫描不会阻塞地图 UI 或无限占用内存。

## Phase 4 — 服务端文件读取与栅格验证

任务：
- 让 RustGIS provider 使用服务端文件路径，或实现受控文件访问适配。
- 如使用 HTTP 文件接口，支持正确的 Range（如果前端/格式路径需要），验证 Content-Length、Content-Range 和断点读取。
- 验证 GeoTIFF、COG、DEM、至少两种矢量格式。
- 对 10 GB 非 COG TIFF 测试内存、首屏时间和缩放体验。
- 只有实测需要时才加 overview/COG 派生缓存。

完成条件：
- 服务端不能读取未配置目录之外的文件。
- 大 TIFF 不被整体读入内存。
- 缓存可清除、可重建，不是唯一数据副本。

## Phase 5 — PostgreSQL/PostGIS 浏览

任务：
- 保存数据库连接的非秘密配置。
- 密码不进入工程、日志、URL 或 API 返回。
- 浏览有权限访问的数据库、schema、表、视图和空间列。
- 表按需添加为图层。
- 处理无权限、连接断开、对象删除、表没有空间列等错误。
- 确认多数据库时逐数据库建立连接。

完成条件：
- 重启后连接配置仍存在；密码安全恢复或要求重新输入，行为清楚。
- 无权限对象不导致应用崩溃。
- 工程引用能识别数据库/schema/table/geometry column。

## Phase 6 — 缺失图层恢复与部署

任务：
- 打开工程时检查外部图层引用。
- 缺失层标记 unavailable 且不渲染。
- 数据恢复后允许重新验证/恢复。
- 完成 Windows、Linux、WSL、Docker 部署说明。
- Docker volume 挂载保证工程、配置、缓存跨容器重建保留。

完成条件：按 `ACCEPTANCE_TESTS.md` 执行全部自动化测试和必要手动测试；已知限制明确记录。

## 实施顺序原则

- 每个 Phase 都独立审查，不能一口气跨越所有阶段。
- 不要在 Phase 2 前大幅重构 UI。
- 不要为追求“完美架构”引入认证、消息队列、独立瓦片服务或复杂数据库。
- 如果上游代码结构与本计划不匹配，先说明差异，再调整计划。
